# 效能分析與 bf16

← [[工具 總覽]] · [[COALA 索引]]

> [!note] 這是**主題筆記**不是檔案筆記
> 原始腳本放在 [[test.py]]（沙盒）裡，已被覆寫。結果記錄在這裡。
> 若要重跑需重寫 `smoke_gpu.py` 和 `profile_step.py`。

---

## 問題

首次煙霧測試實測 **1.04 s/it**（batch=4），推算：

| 資料集 | 10 epochs |
|---|---|
| train-clean-100 | 21 小時 |
| train-960 | **8.5 天** ❌ |

8.5 天在共用伺服器上不現實 —— 中間只要有人要用卡、或機器重開就得重跑。

---

## VRAM 實測（batch=4, fp32, RTX 3090）

```
  [起始              ] 目前  0.00 GB / 峰值  0.00 GB
  [encoder 上 GPU    ] 目前  2.43 GB / 峰值  2.43 GB
  [adapter + ctc     ] 目前  2.45 GB / 峰值  2.45 GB
  [encoder forward   ] 目前  2.49 GB / 峰值  2.80 GB
```

> [!success] 峰值 2.80 GB / 24 GB → 還剩 21 GB，不需要 fp16
> 剩下要給 SmolLM2（約 0.5 GB）、兩組 LoRA、優化器狀態（可訓練只有 5.7M 可忽略），
> 以及 **Stage 2 的 121 次 forward activation**（真正的壓力來源）。

順便確認壓縮能跑：

```
input_features (4, 80, 3000) → encoder (4, 1500, 1280)
→ adapter (4, 375, 576) → ctc logits (4, 375, 29)

壓縮（隨機初始化）: 375 -> 158 / 172 / 219 / 196 tokens
```

> [!tip] 壓縮數字的解讀
> 隨機初始化下壓掉約一半，比預期多。原因是**隨機初始化的 Linear 會讓相鄰 frame 預測出同一個類別** —— 音訊相鄰 frame 本來就相似，經過沒訓練過的線性層輸出也相似，argmax 常常相同，被「與前一個相同就刪掉」的規則收掉。**不是 bug。**
>
> **對照基準**：訓練好之後壓縮結果應接近**實際字元數**。第一句的 `ctc_ids` 是 89 → 理想是 `375 → 89`。現在 158，方向對但還沒學會。
> **這個數字可當作「CTC 有沒有真的學到對齊」的檢查指標。**

## Profiling 結果

```
batch_size = 4
  encoder (fp32)          759.4 ms
  encoder (bf16)          193.7 ms   加速 3.92x
  完整 forward            833.5 ms
  forward+backward+step   924.4 ms   ← 真實訓練步

  encoder 佔完整步的    82.1%

不同 batch size 的每句成本（encoder fp32）:
  bs= 4:   775.7 ms 總計,  193.9 ms/句, 峰值 3.37 GB
  bs= 8:  1467.6 ms 總計,  183.4 ms/句, 峰值 3.72 GB
  bs=16:  3080.4 ms 總計,  192.5 ms/句, 峰值 4.41 GB
```

> [!important] 計時的兩個要點
> - **前幾次當暖機丟掉**（CUDA kernel 第一次執行要編譯 / 載入）
> - **`torch.cuda.synchronize()` 必須在計時前後呼叫** —— CUDA 操作是**非同步**的，不同步的話量到的是「送出指令的時間」而非「實際執行完的時間」

---

## 三個結論

> [!important] 1. Whisper encoder 佔 82% —— 唯一值得優化的地方
> 它**凍結卻每 epoch 重算**。encoder 的參數量是 LM 的 4.7 倍，序列長度是 LM 的 9 倍。

> [!important] 2. bf16 加速 3.92x（遠超預期的 2x）
> 原因：**RTX 3090 的 tensor core 支援 bf16 但不支援 fp32**。用 fp32 只能走一般 CUDA core，等於放著專用硬體不用。
>
> **這不是「犧牲精度換速度」，而是本來就該走的路徑。**

> [!important] 3. 加大 batch 完全無效
> 每句成本幾乎不變（193.9 / 183.4 / 192.5）→ GPU 在 bs=4 時**已經算到飽**，不是在等資料。
>
> **好消息：論文指定的 batch size 4 不造成速度劣勢，可忠實照論文設定跑，不必為速度偏離它。**

## bf16 數值驗證

換 bf16 之前必須確認輸出沒有實質偏差 —— 不能因為快就直接換。

```
fp32 範圍 [-11.961, 28.055]  std 0.8751
bf16 範圍 [-11.958, 28.023]  std 0.8746
平均絕對誤差 0.005779   →  MAE/std = 0.66%
餘弦相似度 0.999476
逐元素相對誤差 10.270%     ← ⚠️ 壞指標，見下
```

**0.66% 符合 bf16 理論精度**（8 bit 尾數 → 2⁻⁸ ≈ 0.39%，加 32 層累積誤差）。

而且 adapter 是**跟著這個輸出一起訓練**的，會自己適應 bf16 的分布。只要輸出穩定（同輸入給同結果），這點誤差不影響學習。

**最終確認 —— 過擬合測試對照**：

| | fp32 | bf16 |
|---|---|---|
| step 200 `ce` | 0.0017 | **0.0015** |
| step 200 `ctc` | 1.134 | **1.075** |

幾乎相同（甚至略好）→ bf16 可安心使用。

> [!warning] 指標選擇的教訓
> 逐元素相對誤差 `|a−b|/(|a|+eps)` 算出 **10.27%**，看起來很糟 —— 但它被**接近零的小值主導**了。
>
> encoder 輸出 std 是 0.875，有大量元素接近 0。當分母是 0.001 而誤差是 0.0001 時相對誤差就是 10%，但那個元素對結果毫無影響。
>
> **驗證含大量接近零值的張量時，相對誤差是壞指標。該用「MAE / std」或餘弦相似度。**

## 採用的寫法（已套用到 [[model.py]]）

```python
with torch.no_grad(), torch.autocast("cuda", dtype=torch.bfloat16):
    out = self.encoder(input_features)
x = out.last_hidden_state.float()     # 必須轉回 fp32 給可訓練的 adapter

h = self.adapter(x)                   # ⚠️ 必須在 with 外面
ctc_logits = self.ctc_head(h)         # ⚠️ 必須在 with 外面
```

> [!danger] 那兩行絕不能放進 with
> | 放錯位置 | 後果 |
> |---|---|
> | 在 `no_grad` 裡 | adapter / CTC head **拿不到梯度**，永遠學不到。但 loss 仍會降（LoRA 還在學）→ **極難察覺** |
> | 在 `autocast` 裡 | 可訓練 Linear 用 bf16 算，梯度精度受損 |
>
> `.float()` 放 with 內或外**無功能差異**（autocast 不覆寫明確的型別轉換），放外面只是視覺上更清楚。

## 修正後的時間預算

每步 `924.4 − 759.4 + 193.7 = 358.7 ms`（實測 train-clean-100 約 380 ms，多出的是每句的 Python 迴圈）

| 資料集 | fp32 | bf16 |
|---|---|---|
| train-clean-100 × 10 ep | 21 小時 | **8.3 小時** |
| train-960 × 10 ep | 8.5 天 | **2.9 天** |

## 未採用的備案（若 2.9 天仍太久）

**預先算好 encoder 輸出存檔。** 因為 encoder 凍結，輸出永遠相同，算一次存起來重複用。

```
每句 (1500,1280) fp16 = 3.84 MB
train-clean-100:  28539 句 ×  3.84 MB = 110 GB
train-960:       281241 句 ×  3.84 MB = 1.08 TB
```

`/mnt/disk2` 還有 **4.1 TB**，兩者都放得下。預估可再加速至 **1.3 天**。

代價：一次性生成時間（960h 約 3.8 小時）+ 之後無法對音訊做資料增強（論文未用）。

> [!note] 另一個可能的優化點（還沒做）
> 剩下那 165 ms 裡，有一部分是 `forward_stage1` 的**逐句 Python 迴圈**（每句都要 `ctc_compress` + tokenize + embedding 查表）。
> 實測 train-clean-100 是 380 ms 而非預估的 359 ms，差額應該就在這裡。
> 若要優化：把 tokenize 的結果快取起來（instruction 的 seg1 對所有句子完全相同，不必每句重算）。
